# ADR-009：数据库 Schema 推导与范式纪律

- 状态：Proposed
- 日期：2026-10-01

## Context

后端将在持久化步骤（Development Plan 步骤 6）首次创建 PostgreSQL 表，首批候选为 Repository、Scan、
Job 元数据（ADR-002）。数据库设计既要可验证也要可学习：过早画 ER 图会让结构迎合想象而非真实查询；
无纪律的例外（随意 JSONB、随意冗余）会让不一致无处追溯。约束前提：ADR-002 规定存储职责，ADR-006
延后 CodeGraph 物理存储，CLAUDE.md 要求数据库访问走统一数据层。

## Decision

1. **从访问模式反推**：每张表先写出它必须回答的查询与业务不变量，再倒推字段、主键与外键；每个
   字段和索引都必须能指向具体查询或不变量，指不上的不进第一版。
2. **默认 3NF + 例外登记制**：判据是“重复存储会不会造成不一致”。只允许两类例外——（a）无查询
   意义的快照（整体写、整体读，可放 JSONB）；（b）有测量证据的冗余。JSONB 只放整体读写的数据，
   凡参与 WHERE / JOIN / 排序的字段必须独立成列；每个例外必须登记理由，未登记的例外不允许合入。
3. **三层记录**：Alembic 迁移（机械真源）、表/列注释 COMMENT ON（每张表写“为什么存在”，数据库
   自描述）、`docs/architecture/数据模型.md`（表 → 契约/用例映射与耦合清单）；决策级变化记 ADR
   或修订 ADR-002。
4. **进入条件**：持久化步骤之前不引入 ORM、不建表；`docker/postgres/init.sql` 只维护扩展。
5. CodeGraph 物理存储继续按 ADR-006 延后，本纪律不预判其最终形态。

## Alternatives

- 先画完整 ER 图再实现：结构迎合想象、缺少访问模式依据，后续迁移成本高，拒绝。
- 全库允许 JSONB“灵活动态列”：初期省事，但查询、约束与不一致追溯能力快速流失，拒绝。
- 立即锁定最终范式与全部存储（含 CodeGraph）：缺乏真实数据证据，违反 ADR-002/006 的测量原则，拒绝。

## Consequences

- 首批元数据表的字段与索引都绑定真实用例；未被引用的设计不进入第一版。
- 范式例外成为可审计清单，同时是项目“学习数据库设计”的素材。
- 数据模型文档与表注释是“第三视图”理念在自身仓库的先行实践（文档先行、UI 后至）。
- 本 ADR 在首个真实 Schema 落地并通过访问模式评审后复审转 Accepted。
