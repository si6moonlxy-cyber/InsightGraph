## 3. 访问模式清单

每一节的结构固定为：**为什么存在 → 必须回答的查询 → 倒推的字段与索引 → 不进第一版的**。

### 3.1 CodeGraph Artifact（JSON，非关系表）

**为什么存在**

CodeGraph 是本系统的核心分析产出，必须**可保存、可重载、可比较**（步骤 6 目标），
且必须字节级确定（步骤 4 完成门槛）。ADR-006 决定第一阶段不落库，由
`CodeGraphRepository` 端口隔离存储形态。

**必须回答的查询**

查询集合的**唯一真源是端口本身**（`backend/app/domain/codegraph/ports.py`，13 行）：

| 编号 | 操作 | 触发场景 |
| --- | --- | --- |
| A1 | `save(graph: CodeGraph) -> None` | 扫描完成后持久化 |
| A2 | `get(repository_id, revision) -> CodeGraph \| None` | 展示 / 对比 / 重载；不存在返回 `None` |

端口只有两个操作，所以 Artifact 存储**只需要回答两个问题**。

**由此倒推的存储要求**

| 要求 | 来源 |
| --- | --- |
| 定位键 = `(repository_id, revision)` | 与域模型一致（`CodeGraph.repository_id` + `.revision`） |
| **原子写入**：临时文件 → fsync → 原子 rename | 完成门槛「中断写入不会留下被误认为完整的 Artifact」 |
| **内容哈希**：保存前后一致；并提供独立的重算入口 | 完成门槛「保存再读取不改变领域对象」 |
| `schema_version` 存在**文件内**，不进文件名 | 它是契约版本（ADR-010），不是定位键 |
| 路径布局 `<artifact_root>/<repository_id>/<revision>.json` | `repository_id` 不含 `:`（ADR-010 强制），可安全作目录名 |

**不进第一版的**

`list_revisions` / `delete` / `exists` / 按 parser_version 检索 —— 端口未定义，
无查询指向。

### 3.2 `scan` 表

**为什么存在**

每次扫描是一次分析事件，其结局必须可查、可追溯。它是 ADR-011 三种结局
（`completed` / `partial` / `failed`）的持久化落点，也是定位 CodeGraph Artifact 的索引。

**必须回答的查询**

| 编号 | 查询 | 触发场景 | 现有依据 |
| --- | --- | --- | --- |
| S1 | 按 `(repository_id, revision)` 取该次扫描的结局、统计与 Artifact 契约版本 | 判断某 revision 是否已扫过、结果如何、该用哪个 schema_version 读 Artifact | `ScanResult` 已含这两个字段；`CodeGraphRepository.get` 用同一键 |
| S2 | 列出某 `repository_id` 的全部扫描，按时间倒序 | 历史列表、选择对比基线 | 步骤 8 API 用例 |
| S3 | 写入一次扫描结果 | 扫描完成后 | `ScanResult` |

**倒推的字段**

| 字段 | 指向查询 | 说明 |
| --- | --- | --- |
| `id` | S1·S2·S3 | 扫描记录自身标识（代理键） |
| `repository_id` | S1·S2 | 定位键之一 |
| `revision` | S1 | 定位键之一；**可为 NULL**——`ScanResult.revision` 是 `str \| None`，`failed` 结局允许无 revision |
| `status` | S1·S2 | `completed` / `partial` / `failed`（ADR-011 闭合集合） |
| `files_collected` / `files_analyzed` / `files_failed` | S1 | `ScanStats` 漏斗计数 |
| `graph_schema_version` | S1 | 读 Artifact 时判定契约版本 |
| `parser_version` | S1 | 判定产出者实现版本（与契约版本相互独立，见 ADR-010） |
| `created_at` | S2 | 排序键 |

**索引**

| 索引 | 指向查询 |
| --- | --- |
| PK (`id`) | S1 |
| INDEX (`repository_id`, `created_at` DESC) | S2 |

**刻意不加的**：`(repository_id, revision)` 上的 UNIQUE 约束 —— 见 §5 待评审第 1 条。

### 3.3 `scan_error` 表（`scan` 的 1:N 子表）

**为什么存在**

`ScanResult.errors` 是变长列表，且需要按扫描、按严重度、按错误码检索。
按 ADR-009 第 2 条，**参与 WHERE / 聚合的数据不得放 JSONB**，因此独立成表。

**必须回答的查询**

| 编号 | 查询 | 触发场景 |
| --- | --- | --- |
| E1 | 取某次扫描的全部错误（按严重度/阶段排序） | 结果详情展示 |
| E2 | 统计某段时间内各 `code` 的出现次数 | 解析质量趋势——判定「局部失败是否在恶化」 |

**倒推的字段**

| 字段 | 指向查询 |
| --- | --- |
| `id` | 代理键 |
| `scan_id` | E1（FK → `scan.id`） |
| `stage` | E1（`collect` / `analyze` / `persist`） |
| `code` | E2（ADR-011 定义的稳定错误码闭合集合） |
| `severity` | E1（`local` / `fatal`） |
| `message` | E1 |
| `file_path` | E1（可空——错误不一定归属具体文件） |

**索引**：PK (`id`)；INDEX (`scan_id`) 供 E1；INDEX (`code`, `created_at`) 供 E2。

### 3.4 向量存储（证据向量）

**归属**

ADR-002：**pgvector 保存「证据向量」**。数据源是 `Evidence`，消费者是 GraphRAG 检索层。

**为什么存在**

「这个项目为什么被认为具备某种技术能力」这类问题要先按**语义相似度**召回一批候选证据，
再沿证据关系展开——前者是纯图遍历回答不了的。

**必须回答的查询**（预计消费者 = 步骤 9 的 GraphRAG 检索层）

| 编号 | 查询 | 触发场景 |
| --- | --- | --- |
| V1 | 给定 query 向量，取最相似的 top-k 条证据（可按 `repository_id` 过滤） | 语义检索入口 |
| V2 | 为一批 `Evidence` 写入 / 更新 embedding | 证据抽取（步骤 9） |
| V3 | 按 `evidence_id` 取回 embedding | rerank 与调试 |

**为什么现在不进第一版（硬阻塞，与排期无关）**

| 前置条件 | 状态 | 影响 |
| --- | --- | --- |
| pgvector 扩展 | ✅ 已装（0.8.7，`docker/postgres/init.sql` 建） | 基础设施就绪 |
| `Evidence` 上的 embedding 字段 | ❌ **领域模型无此字段** | 没有可写入的数据 |
| **embedding 模型选型 → 维度 N** | ❌ **全仓无记录** | **`vector(N)` 的 N 无法确定** |
| 检索层（V1 的消费者） | ❌ 步骤 9 未开始 | 没有调用方 |

**维度为什么不能先猜一个**：列类型 `vector(N)` 的 N 由 embedding 模型决定；
改 N 意味着重建列 + 重建 HNSW 索引 + 重新灌全部向量。ADR-009 第 1 条
（指不上的不进第一版）与第 2 条（判据是「重复存储会不会造成不一致」）都要求先有真实查询与数据。

**解阻塞路径（按顺序）**

1. **定 embedding 模型选型** → 得到维度 N（需回答：检索对象是代码还是文档？本地推理还是 API？
   中文与代码如何兼顾？）
2. 在 `domain/evidence/models.py` 的 `Evidence` 上增加 embedding 字段，
   或引入独立的向量记录模型
3. 步骤 9 设计检索层，冻结 V1–V3 的精确形态（top-k 口径、过滤维度、rerank 分工）
4. 届时按本文既有格式补一份与 `scan` 表同规格的字段 / 索引推导，再建表

### 3.5 不进第一版的表

| 候选 | 不进的理由（ADR-009 第 1 条：指不上的不进第一版） |
| --- | --- |
| `repository` | 现有域模型中 `repository_id` 是**调用方提供的不透明字符串**，没有仓库级属性（第一阶段只接收本地路径，无远程 URL / 默认分支）；「仓库列表」类查询可由 `scan` 表的 `repository_id` 直接回答，无需独立表。见 §5 待评审第 3 条。 |
| `job` | ADR-002 列举了 Job 元数据，但其查询依赖步骤 8 的任务模型（状态机、重试、取消语义），当前**写不出具体查询**。待步骤 8 定义任务状态机后补。 |
| `source_manifest` | `SourceManifest.files` 是 `(path, content_hash)` 列表，用途是确定性审计与跨扫描文件变化对比。当前无查询指向，且它同属确定性产物——是否一并纳入 Artifact 纪律见 §5 待评审第 4 条。 |
| **证据向量表** | 见 §3.4：维度未知、领域模型无 embedding 字段、消费者未建立。 |

## 5. 待评审（写本文时发现的真问题）

### 5.1 ⚠️ `(repository_id, revision)` 在 worktree_dirty 下语义冲突

**问题**：`SourceManifest.worktree_dirty` 表示采集时存在未提交改动，此时清单反映
**工作区状态**而非纯 revision 快照。而 `CodeGraphRepository.get` 的定位键只有
`(repository_id, revision)`。

于是：同一个 revision 上对 dirty 工作区扫描两次，**两次内容可能不同，但定位键相同** ——
A2 只会取到一份，`save` 的行为未定义。

**候选处置**：

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| (a) `save` 检测冲突：已存在且内容哈希不同 → 拒绝并报错 | 保住「同一键 = 同一内容」不变量 | 合法重扫被拒，需人工清理 |
| (b) 定位键扩为 `(repository_id, revision, content_hash)` | 天然支持多份 | 与端口签名不一致，需改 `CodeGraphRepository` |
| (c) `save` 幂等覆盖，scan 表记录实际内容哈希 | 最简单 | 丢失历史；「同一键 = 同一内容」不变量失效 |

**建议 (a)**，并把冲突计入 `ScanErrorCode.STORAGE_ERROR`（已有码，不需扩集合）。
**需 Human 决策。**

### 5.2 `save` 对已存在 Artifact 的策略

与 5.1 相关但独立：`parser_version` 变化时会合法地产出不同的图而 revision 不变。
是否允许 `save` 在这种情况下覆盖？若不覆盖，`parser_version` 的演进如何落地？

### 5.3 `repository` 表延后是否符合 ADR-002 意图

本文 §3.4 建议第一版不建 `repository` 表。ADR-002 列举了「Repository 元数据」，
但它处于 Proposed 且声明「获得真实查询样本后复审」。需确认：是接受本建议，
还是先建一张最小 `repository` 表（仅 `repository_id` + `created_at`）以承载 ADR-010 的
`repository_id` 格式不变量。

### 5.4 `SourceManifest` 是否纳入 Artifact 纪律

`SourceManifest` 与 `CodeGraph` 同属确定性产物，同样有 `schema_version`。
是否复用 `CodeGraphRepository` 的原子写入 + 内容哈希机制（另开端口或参数化），
还是留待出现真实查询时再定？
